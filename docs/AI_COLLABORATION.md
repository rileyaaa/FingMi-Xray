# AI 协作开发准则

本文件集中维护 AI 在本仓库中与用户共同开发时必须遵守的执行限制。产品行为、工程架构、构建与 Xray parity 规则仍分别以 `PROJECT.md`、`DEVELOPMENT.md`、`RECOVERY.md` 和对应测试为准；其他文档不再单独维护一套 AI 操作规则。

## 1. 禁止原地轮询 CI / Actions

- 同一个 GitHub Actions run 在同一工作阶段最多主动检查一次状态，禁止连续重复查询 run / jobs / logs 只为了等待 `queued` / `in_progress` 变成完成。
- 如果该次检查仍未完成，立即继续做其他有实际产出的审计、测试、代码或文档工作。
- 如果没有其他可做的工作，就结束当前回复并报告当前状态；不要占着会话等待 CI。
- 只有 run 已完成、步骤发生实质变化、或需要定位明确失败时，才继续读取该 run 的 jobs / logs。

## 2. Actions 状态必须从最新 runs 列表重新确认

- 每次准备向用户报告 Actions 当前状态前，先刷新仓库最新 runs 列表，再从该列表定位目标 run。
- 不得把之前读取的单个 run 状态、旧 jobs 结果或旧日志时间戳当成当前状态。
- 只有最新 runs 列表确认目标 run 已完成后，才读取该 run 的 jobs / logs 来确认具体成功步骤或失败原因。
- 在说“还在执行 / 已经完成 / 已经失败”之前，必须完成上述重新确认。
- 项目 workflow 的临时自动触发只用于必要验证；验证完成后立即恢复 `workflow_dispatch`，并再次确认 current-main 与 publish workflow 均为纯手动。

## 3. 会话接近平台时限时立即交接返回

- 如果 AI 判断当前会话接近平台时限、上下文容量限制或可能被系统中断，不得继续开启新的长流程、轮询、批量审计或大范围修改。
- 应立即结束当前工作阶段并向用户返回可继续接手的信息，包括：
  - 当前 `main` HEAD；
  - 已完成并提交的工作；
  - 尚未完成或正在验证的事项；
  - 临时 workflow trigger 是否已经撤回；
  - 下一步最具体的操作入口 / 文件 / run / commit。
- 不要等到会话被强制中断后再留下半截工作。
- 用户确认后会在当前或新会话再次发送“继续工作”；下一位 AI 应直接按交接状态继续，不重复已经确认的检查和问题。

## 4. 及时维护项目文档，但禁止流水账式更新

- 代码、架构、构建链、验证入口、发布边界或历史证据发生**稳定且会影响后续开发判断**的变化时，应在同一工作阶段及时更新对应文档；不要把文档维护拖到若干次提交之后，更不要依赖聊天上下文代替仓库文档。
- 文档只写“当前长期成立的事实、约束、复现方式、验证入口和必要的故障结论”，不按日期、commit、Actions run 或尝试次数记录开发过程。Git 历史负责回答“哪次提交改了什么”，GitHub Actions 负责保存 run / job / log。
- 不建立或继续扩展按日期排列的开发日志。调试中的失败尝试、临时 trigger、一次性 run id、阶段性 commit sha、已经被后续结果取代的状态，不进入长期文档；只有当某个 SHA / run / hash 本身是可重复取证或固定 provenance 的必要标识时才保留。
- 调试得到的重要结论如果会长期影响维护，应直接整理进所属主题章节，例如“构建依赖”“Binder 生命周期”“验证规则”，而不是追加一篇“本轮做了什么”。
- 不在多份文档复制同一段过程说明。优先修改负责该主题的 canonical 文档，其他位置只保留必要的定位说明和链接。
- 对验证结论必须准确标注证据层级。静态比较、JVM / 单元测试、Gradle 编译、APK assemble、Actions、模拟器 / 真机运行不能互相冒充；没有实际完成的层级不要写成已验证。
- 每次准备交接或结束一段会改变项目长期状态的工作前，应检查受影响的文档是否已经同步；若代码事实已变化而文档仍旧，应先修文档再交接。

### 文档归属

- `README.md`：面向仓库读者的项目概览、版本基线和文档导航。
- `PROJECT.md`：产品边界、模块职责和长期架构约束；不记录 Actions run、发布进度或调试过程。
- `DEVELOPMENT.md`：当前源码结构、构建链、上游同步方式和稳定验证规则；不承担开发流水账。
- `RECOVERY.md`：旧发布版历史事实、faithful 恢复与 native provenance；不记录 current-main 的日常开发过程。
- `apk-reference/README.md`：可长期复核的最小 APK 文本证据索引；一次性日志和中间文件留在 artifact / 工作目录。
- `tests/README.md`、`compat/README.md`、`recovery/README.md`：对应目录职责、长期入口或材料定位发生变化时同步更新。
- `ORIGINAL_README.md`：冻结的旧发布说明，不随当前开发改写。

## 执行优先级

这些限制属于 AI 协作流程的固定约束。若后续交接信息与本文件冲突，以用户最新明确指令为最高优先级；否则后续 AI 必须继续遵守本文件。
