# AI 协作开发准则

本文件用于约束 AI 在本仓库中与用户共同开发时的执行方式。它不是产品行为规范，也不替代 `DEVELOPMENT.md` 中的工程设计、构建和 Xray parity 约束。

## 1. 禁止原地轮询 CI / Actions

- 同一个 GitHub Actions run 在同一工作阶段最多主动检查一次状态，禁止连续重复查询 run / jobs / logs 只为了等待 `queued` / `in_progress` 变成完成。
- 如果该次检查仍未完成，立即继续做其他有实际产出的审计、测试、代码或文档工作。
- 如果没有其他可做的工作，就结束当前回复并报告当前状态；不要占着会话等待 CI。
- 只有 run 已完成、步骤发生实质变化、或需要定位明确失败时，才继续读取该 run 的 jobs / logs。

## 2. Actions 状态必须从最新 runs 列表重新确认

- 每次准备向用户报告 Actions 当前状态前，先刷新仓库最新 runs 列表，再从该列表定位目标 run。
- 不得把之前读取的单个 run 状态、旧 jobs 结果或旧日志时间戳当成当前状态。
- 只有最新 runs 列表确认目标 run 已完成后，才读取该 run 的 jobs / logs 来确认具体成功步骤或失败原因。
- 在说“还在执行 / 已经完成 / 已经失败”之前，必须完成上述重新确认。
- 项目 workflow 的临时自动触发只用于必要验证；验证完成后立即恢复 `workflow_dispatch`，并再次确认 current-main 与 publish workflow 均为纯手动。

## 3. 会话接近平台时限时立即交接返回

- 如果 AI 判断当前会话接近平台时限、上下文容量限制或可能被系统中断，不得继续开启新的长流程、轮询、批量审计或大范围修改。
- 应立即结束当前工作阶段并向用户返回可继续接手的信息，包括：
  - 当前 `main` HEAD；
  - 已完成并提交的工作；
  - 尚未完成或正在验证的事项；
  - 临时 workflow trigger 是否已经撤回；
  - 下一步最具体的操作入口 / 文件 / run / commit。
- 不要等到会话被强制中断后再留下半截工作。
- 用户确认后会在当前或新会话再次发送“继续工作”；下一位 AI 应直接按交接状态继续，不重复已经确认的检查和问题。

## 执行优先级

这些限制属于 AI 协作流程的固定约束。若后续交接信息与本文件冲突，以用户最新明确指令为最高优先级；否则后续 AI 必须继续遵守本文件。
